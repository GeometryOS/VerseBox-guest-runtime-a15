# 验证与发布操作

这一篇说明三件事：这些改动交付前跑过什么，还有什么没有验证，以及维护者发布一次要按什么顺序操作。

## 1. 交付前跑过的检查

### 1.1 三个脚本的语法

三个脚本都是 ES 模块，用 Node 自带的语法检查即可，正常时没有任何输出。

```bash
node --check .github/scripts/collect-release-assets.mjs
node --check .github/scripts/generate-release-notes.mjs
node --check .github/scripts/update-release-index.mjs
```

### 1.2 两个工作流的 YAML

用真正的解析器读一遍，比只看缩进可靠。解析通过之后还要断言结构，包括发布步骤的先后顺序、手动触发只有两个输入、正文路径指向生成的文件、构建工作流里不再有任何发布步骤、构建工作流的推送触发带着索引目录的跳过规则。

```bash
python3 -c "import yaml,sys; [yaml.safe_load(open(p, encoding='utf-8')) for p in sys.argv[1:]]" \
  .github/workflows/build.yml .github/workflows/release-publish.yml
```

### 1.3 每个步骤里的 shell

YAML 解析只证明缩进合法，不证明里面的 shell 能读。做法是把每个步骤的命令块单独落成文件，逐个用 shell 的语法检查跑一遍。字节数、引号配对这类错误在这一步就会露头，不必等推上去才发现。

### 1.4 用夹具跑一遍脚本

夹具建在系统临时目录，不建在仓库里，也不需要动仓库的标签。夹具里造两个标签，区间中间放三条提交，标签之后再放一条提交，然后按真实顺序跑三个脚本。

| 行为 | 判据 |
| --- | --- |
| 区间只含上一个标签到本标签的提交 | 正文里没有标签之后那条提交的标题 |
| 标题由版本段与日期拼成 | 标题文件匹配版本段接八位日期 |
| 提交标题里的星号与下划线被转义 | 正文里出现反斜杠转义后的原文 |
| 版本与 ROM 版本各占一行 | 正文里两者分别出现，且不是同一个值 |
| 同一个标签重发只留一条并覆盖内容 | 两次写入后条目数仍为一，标题是第二次的值 |
| 同一个版本换一个标签再发 | 条目数变为二，两条的标签不同、日期不同 |
| 旧标签重发后排到末尾 | 条目数不变，最后一条的标签是重发的那个 |
| 已有一百条时新增一条 | 条目数仍为一百，最早的那条消失 |
| 版本写成数字 | 脚本非零退出并提示手改 |
| 记录缺标签字段 | 脚本非零退出并提示手改 |
| 标签参数不合法 | 脚本非零退出并说明格式 |
| 打包报告与配置不一致 | 脚本非零退出并说明要重建这个标签 |
| 零字节文件 | 收集脚本非零退出 |
| 只有第一个标签时 | 正文给出说明，且没有完整变更链接 |

这一轮的结果是三十二项断言全过，其中正文与收集十六项，索引十六项。

## 2. 还没有验证的部分

| 项 | 现状 | 怎么验 |
| --- | --- | --- |
| 真实 GitHub 运行 | 两个工作流尚未在本仓库跑过 | 第一次发布先打开试跑开关 |
| 跨运行取附件 | 依赖那次运行的附件没有过期 | 报附件不存在时重跑该标签的构建 |
| 索引写回默认分支 | 依赖默认令牌的推送权限 | 看写回索引那一步的日志 |

## 3. 发布一次的操作顺序

1. 提交并推送改动，确认工作区干净。
2. 打一个标签并推送，标签形如版本段接构建后缀。
3. 等构建在这个标签上变绿，没有绿的构建，第二道闸门一定拦下来。
4. 手动运行发布工作流，填同一个标签，打开试跑开关。
5. 读日志里打印的标题与正文，确认标题只有版本与日期两段，确认更新条目落在两个标签之间。
6. 关掉试跑开关再跑一次，正式发布。
7. 到发布页核对标题、正文里的哈希与附件列表一致、附件齐全，再到默认分支确认索引多了一条。

## 4. 失败先看哪里

| 现象 | 先看 |
| --- | --- |
| 第二道闸门报没有成功的构建 | 日志列出同一提交的运行，看名称与结论 |
| 哈希校验报对不上 | 是哪个文件，以及那次构建是否被重跑过 |
| 第四道闸门报打包器错误 | 打包器列出的问题条目，回查打包脚本 |
| 正文脚本报浅克隆 | 检出的深度是否为零 |
| 正文脚本报版本不一致 | 配置文件是否在打标签之后改过而没有重新构建 |
| 发布成功但索引没动 | 写回索引那一步的推送与变基记录 |
